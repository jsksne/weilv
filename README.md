# 微律

> 基于 Agentic RAG 与混合检索的青少年个性化健康微干预系统

## 项目简介

**微律**是一套面向儿童青少年的个性化健康微干预系统。

“微”代表微任务、微干预和低负担行动；“律”代表睡眠、运动、学习、休息等健康节律，也代表系统通过持续反馈逐渐发现每个学生自身的行为规律。

项目希望解决的不是“学生不知道怎样更健康”，而是：

> 在学习压力、时间和精力都有限的情况下，如何为不同学生找到当前最容易执行、最适合坚持的健康行动？

系统根据学生的个人画像、考试周期、当天状态、已有活动和历史反馈，从经过审核的健康知识库和微任务库中检索适合当前用户的内容，并生成少量、低负担、可解释的个性化健康行动建议。

项目当前优先实现 **Web 版本**。

第一版核心目标用户为：

> **小学高年级（4～6年级）、初中生与高中生。**

## 一、为什么做微律

青少年的很多健康问题，并不完全来自缺少健康知识。

学生通常知道：

- 久坐不好；
- 长时间用眼需要休息；
- 应该适当运动；
- 应该早点睡；
- 应该增加户外活动。

真正困难的是：

- 学习任务密集，没有时间完成复杂健康计划；
- 考试周和平时的状态完全不同；
- 不同学生愿意接受的任务形式差异很大；
- 同一个学生在不同日期的身体和学习状态也不同；
- 传统健康软件通常设置统一目标，很难持续适应个人变化；
- 普通AI可以回答健康问题，却不一定真正了解“这个学生现在适合做什么”。

因此，微律希望研究：

> AI能否结合个人信息、当天状态和持续行为反馈，为每个学生找到更容易坚持的健康微行动？

## 二、产品定位

微律不是医疗诊断系统，也不是传统运动课程平台。

项目定位为：

> **青少年个性化健康行为辅助与微干预智能系统。**

系统主要围绕：

- 久坐；
- 连续用眼；
- 户外活动；
- 运动；
- 睡眠准备；
- 学习间歇；
- 轻量放松与恢复；

等健康行为提供每日微任务。

核心原则：

1. 每日只推荐少量任务；
2. 任务应保持低负担；
3. 推荐必须结合当前用户状态；
4. 推荐结果可以解释；
5. 用户可以替换、跳过或调整任务；
6. 不通过扣分、排名或连续签到制造压力；
7. 安全规则优先于AI推荐；
8. 系统学习的是“怎样更容易行动”，而不是评价学生身体好坏。

## 三、核心产品闭环

```text
建立用户画像
      ↓
读取当天状态
      ↓
读取历史行为与个人记忆
      ↓
用户提出问题或系统产生推荐需求
      ↓
问题理解
      ↓
子问题拆分
      ↓
混合检索
      ↓
Reranker重排序
      ↓
安全规则过滤
      ↓
RAG构建上下文
      ↓
程序从正式白名单选择微任务，LLM只解释已选择任务
      ↓
用户执行 / 完成 / 部分完成 / 替换 / 跳过
      ↓
记录反馈
      ↓
更新用户记忆库
      ↓
影响下一次推荐
```

项目最重要的结果不是：

> “用户完成了多少任务。”

而是：

> **系统能否通过持续反馈，逐渐知道什么任务、什么时间和什么强度，更适合当前这个学生。**

例如：

```text
基础相关性排序
      ↓
Safety 过滤后保留正式白名单任务
      ↓
读取与候选 task_id 对应的结构化反馈或明确偏好
      ↓
对安全候选做有限排序校正
      ↓
任务正文和正式时长保持不变
```

## 四、个性化设计

个性化是微律最重要的项目亮点之一。

系统综合以下信息形成用户上下文。

### 1. 用户基础画像

例如：

- 学习阶段；
- 日常作息；
- 通常可用时间；
- 用户主动设置的健康目标；
- 用户偏好的任务类型。

### 2. 当天上下文

例如：

- 是否处于考试周期；
- 当天可用时间；
- 疲劳程度；
- 身体不适情况；
- 已有运动或活动；
- 用户主动填写的当前状态。

### 3. 历史行为

例如：

- 哪些任务经常接受；
- 哪些任务经常完成；
- 哪些任务经常跳过；
- 喜欢多长时间的任务；
- 哪个时间段更容易执行；
- 对推荐任务的反馈；
- 历史替换记录。

这些信息写入用户独立记忆库，并持续影响后续检索和推荐。

## 五、用户独立记忆库

每名用户拥有独立的：

> **User Memory 用户记忆库**

用于保存系统已经了解的个性化信息。

例如：

```text
基础画像
考试状态
可用时间

任务偏好
喜欢的任务
不喜欢的任务

行为历史
接受
完成
部分完成
替换
跳过

时间偏好
任务强度偏好

历史评价
太难
太累
没时间
愿意继续
```

推荐时同时使用：

```text
公共健康知识
+
当前用户记忆
+
当天状态
+
当前问题
```

使同一个问题面对不同学生时产生不同结果。

用户记忆采用 Elasticsearch 进行存储，并通过独立索引或等效的严格逻辑隔离方式实现不同用户数据的独立管理。

## 六、AI与RAG技术路线

微律采用：

> **子问题拆分 + BM25 + 向量检索 + Reranker + RAG + LLM**

整体流程：

```text

+
当天状态
+
历史行为
+
用户问题
        │
        ▼
    输入风险分流
        │
        ├── 高风险：停止普通推荐并提示求助
        │
        ▼
    用户问题理解
        │
        ▼
     子问题拆分
        │
        ▼
针对每个子问题构造 Query
        │
        ├─────────────────────┐
        ▼                     ▼
ES向量语义检索             ES BM25检索
Cosine Similarity
        │                     │
     Top 10                Top 10
        │                     │
        └─────────┬───────────┘
                  ▼
             候选结果
                  │
                  ▼
          qwen3-rerank API
                  │
                  ▼
             重排序结果
                  │
                  ▼
     任务适用性与停止条件过滤
                  │
                  ▼
           RAG上下文构建
                  │
                  ▼

                  │
```

## 七、为什么需要子问题拆分

复杂用户问题往往同时包含多个健康因素。

例如：

> “最近考试复习很晚，白天一直坐着，脖子有点累，而且晚上睡不好，我今天应该做什么？”

系统不会直接拿整个句子只检索一次，而可以拆成：

```text
子问题1：
考试期间适合什么低负担健康任务？

子问题2：
长时间久坐后适合什么微干预？

子问题3：
颈肩疲劳时哪些任务应该避免或降低强度？

子问题4：
睡眠状态较差时适合什么睡前任务？
```

不同子问题分别检索，再综合结果。

这一机制也是后续升级 Agentic RAG 的基础。

---

## 八、双路混合检索

系统采用两条检索路线。

### 第一路：向量语义检索

知识和微任务经过 Embedding 模型转化成向量后写入 Elasticsearch。

用户问题和拆分后的子问题也转换为向量，通过：

> **Cosine Similarity 余弦相似度**

寻找语义上相似的知识。

每次检索：

> **Vector Top 10**

Embedding采用阿里云 `text-embedding-v4`，第一版固定使用1024维向量。

---

### 第二路：BM25关键词检索

使用 Elasticsearch 的全文搜索能力进行：

> **BM25关键词检索**

用于寻找文字表达和关键词高度相关的知识。

每次检索：

> **BM25 Top 10**

---

## 九、Reranker重排序

两路检索结果：

```text
Vector Top 10
+
BM25 Top 10
```

统一形成候选集合，并发送给：

> **qwen3-rerank API**

进行第二阶段相关性重排序。

Reranker负责解决：

> 第一轮搜索“找到了可能相关的内容”，第二轮进一步判断“到底哪些内容与当前问题最相关”。

最终高质量结果进入RAG上下文。

## 十、Elasticsearch统一数据架构

项目竞赛版统一采用 Elasticsearch。

业务数据与向量数据均使用 ES。

主要负责：

- 用户基础数据；
- 用户画像；
- 用户行为记录；
- 用户历史反馈；
- 用户记忆；
- 微任务数据；
- 健康知识；
- RAG文本；
- Embedding向量；
- BM25全文搜索；
- 向量检索。

竞赛版不再额外引入 MySQL、PostgreSQL 或独立向量数据库作为核心依赖。

第一版使用以下逻辑索引：

```text
source_documents_v1    原始资料元数据、版本、哈希和审核状态
health_knowledge_v1     公共健康知识
micro_tasks_v1         审核微任务
user_profiles_v1       匿名用户画像
user_memory_v1         用户独立记忆
interaction_logs_v1    问答与任务反馈
evaluation_records_v1  测试和问卷结果
```

干净 Elasticsearch 环境可运行以下命令，以正式 `micro_tasks_v1.jsonl`、正式
`embedding_text`、`text-embedding-v4`（1024 维）和冻结 mapping 幂等构建
`micro_tasks_v1`：

```powershell
.\.venv\Scripts\python.exe scripts\bootstrap_micro_tasks.py
```

一致性规则：

1. 浏览器只访问FastAPI，不直接连接Elasticsearch；
2. 刚写入的数据需要立即按ID读取时使用实时GET；
3. 写入后必须立即参与下一次搜索时使用 `refresh=wait_for`；
4. 更新用户画像和用户记忆时使用ES乐观并发控制；
5. 不设计依赖多文档事务的核心流程，并定期制作Snapshot备份。

## 十一、RAG知识库

公共知识库主要包括两类。

### 健康知识库

内容覆盖：

- 久坐；
- 用眼；
- 户外活动；
- 运动；
- 睡眠；
- 学习间歇；
- 轻量恢复。

知识内容需要尽可能保留：

- 来源；
- 主题；
- 适用对象；
- 安全要求；
- 标签；
- 更新时间。

### 微任务库

保存系统允许推荐的具体健康行动。

每个任务可以包含：

- 任务名称；
- 任务内容；
- 所属健康领域；
- 预计时间；
- 活动强度；
- 适用场景；
- 考试周是否适合；
- 安全限制；
- 替代任务。

知识切片和Metadata结构按照合理的RAG工程方式实现即可，不强制要求“一项任务等于一个Document”。

## 十二、从RAG升级到Agentic RAG

第一阶段先实现稳定的基础RAG：

```text
问题
↓
子问题拆分
↓
检索
↓
Reranker
↓
生成
```

基础链路稳定后，升级为：

> **Agentic RAG**

Agent框架确定采用：

> **LangGraph**

Agentic RAG允许系统根据当前问题决定是否：

- 拆解问题；
- 查询公共知识库；
- 查询用户记忆；
- 修改检索Query；
- 再次搜索；
- 检查已有结果是否足够；
- 根据结果继续下一步行动。

升级后的逻辑可以表现为：

```text
理解用户需求
      ↓
制定检索计划
      ↓
拆分子问题
      ↓
执行检索
      ↓
检查结果
      ↓
信息是否足够？
  ├─ 否 → 修改Query → 再检索
  └─ 是
      ↓
综合用户记忆与知识
      ↓
生成个性化建议
```

## 十三、后续升级：协同过滤

在积累一定量真实用户行为数据后，引入：

> **Collaborative Filtering 协同过滤**

RAG主要利用：

> 当前用户 + 知识内容

用户记忆主要利用：

> 当前用户自己的历史行为

协同过滤则进一步利用：

> 与当前用户行为模式相似的其他用户。

例如：

```text
学生A
对某个正式任务给出明确正反馈

学生B
行为模式与学生A相似
```

那么系统可以参考相似用户的历史行为，对学生B的候选任务进行进一步优化。

最终形成三层个性化：

```text
知识相关性
RAG
+
个人历史规律
User Memory
+
相似用户行为
Collaborative Filtering
```

## 十四、安全原则

微律面向青少年，因此安全规则优先于推荐效果。

系统不用于：

- 医疗诊断；
- 疾病判断；
- 药物建议；
- 替代医生；
- 心理疾病诊断；
- 严重疾病风险预测。

当用户主动报告明显疼痛、严重身体不适或其他需要专业处理的情况时，应优先停止普通任务推荐，并提示寻求监护人、学校支持人员或专业机构帮助。

LLM不得绕过任务安全规则自由生成高风险健康建议。

第一版至少实现以下可执行安全策略：

1. 输入风险分流：识别明显疼痛、严重不适、急性风险和求医需求；
2. 任务白名单：只能从经过人工审核的微任务库中选择行动；
3. 适用条件过滤：按年龄阶段、身体状态、场景和风险标签排除不适合任务；
4. 输出校验：禁止诊断、药物建议、高风险运动和夸大效果；
5. 求助提示：触发风险条件时停止普通推荐，建议联系监护人、学校支持人员或专业机构；
6. 审计记录：保存触发的规则、采用的知识来源和最终处理结果。

## 十六、质量评估

项目不把 Recall@K、MRR、NDCG 等偏学术检索指标作为主要评价方式。

主要采用：

> **需求评估问卷 + 模型结果质量评估问卷**

同时保留一组轻量工程验证：使用50～100个有人工来源标注的真实问题检查检索和引用，使用不少于30个风险场景检查安全分流，并记录端到端响应时间。该验证用于发现系统问题，不作为医学效果证明，也不要求搭建复杂的模型横评平台。

### 公开用户数据的用途边界

CEPS、YRBSS、WHO GSHS、PISA 等公开调查数据，只用于了解学生群体的真实分布、设计用户画像字段和生成明确标注的合成测试用户。它们不是微律真实用户的使用记录，不得直接写入 `user_memory_v1`。

协同过滤真正需要的数据结构是：

```text
User × MicroTask × Feedback
```

在真实交互数据达到可用规模前，只允许使用 `synthetic = true` 的合成用户和合成交互进行技术 POC，不得描述成真实产品效果。

### 需求评估问卷

用于验证：

- 青少年主要健康行为问题；
- 用户是否需要低负担任务；
- 可接受的任务数量；
- 可接受的任务时间；
- 对个性化推荐的需求程度；
- 当前同类产品存在的问题。

### 模型质量评估问卷

向参与者直接展示模型产生的实际结果，评价：

- 相关性；
- 个性化程度；
- 可执行性；
- 任务负担；
- 推荐解释是否清楚；
- 执行意愿；
- 整体满意度。

比赛中还可以进行：

```text
普通推荐
VS
个性化RAG推荐
```

对比用户更愿意采用哪种结果。

## 十七、核心创新点

### 创新一：个性化健康微干预

系统不只研究：

> “什么行为健康？”

而重点研究：

> **“当前这个学生最容易真正做到什么？”**

通过用户记忆和持续行为反馈改变后续推荐。

### 创新二：混合检索RAG

采用：

```text
BM25
+
text-embedding-v4 / Cosine Similarity
+
qwen3-rerank
```

提高健康知识和微任务检索质量。

### 创新三：Personal RAG

让用户画像、当天状态和历史行为参与检索过程。

个性化不只发生在LLM最后生成答案时，而是深入到检索阶段。

### 创新四：Agentic RAG

利用 LangGraph 构建Agentic RAG，使系统能够主动：

- 拆分问题；
- 规划检索；
- 重新检索；
- 查询用户记忆；
- 检查信息充分程度。

### 创新五：协同过滤升级

在个人记忆基础上进一步利用相似用户行为，提高任务推荐的个性化程度。

## 十八、当前技术栈

| 层级 | 技术方案 |
|---|---|
| Web前端 | Vue + Element |
| 后端 | Python + FastAPI |
| 业务数据库 | Elasticsearch |

| Knowledge / MicroTask / Memory Vector召回 | `VECTOR_RECALL_K = 10` |
| Memory重排保留 | `MEMORY_RERANK_K = 5` |
| Task最终选择 | 1条正式白名单任务 |
| Reranker | qwen3-rerank（纯文本） |
| Reranker调用 | API |
| Embedding | 阿里云 text-embedding-v4，1024维 |
| LLM职责 | 只解释程序已选择的正式任务，不决定或改写任务 |
| Agent框架 | LangGraph |
| Agent升级 | Agentic RAG |
| 后续推荐升级 | 协同过滤 |
| 质量验证 | 需求问卷 + 模型结果质量问卷 |

## 二十、明确不做什么

竞赛版暂不建设：

- 完整运动课程平台；
- 跑步轨迹和位置社交；
- 医疗诊断系统；
- 药物推荐；
- 疾病风险预测；
- 卡路里惩罚；
- 健康排行榜；
- 强制连续签到；
- 与核心闭环无关的大量健康功能。

项目优先把：

> **个性化检索 → 个性化推荐 → 用户行动 → 用户反馈 → 下一次调整**

这一AI闭环做好。
