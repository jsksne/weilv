## 2. 已确定的交互

以下以“作业很多，不想动”说明期望的理解方式，仅为说明性示例，不要求添加固定话术、关键词分支或对应任务。实现应处理一般的时间、环境、偏好与行动负担约束：

- “作业很多”表示时间可能紧张，不擅自认定确切分钟数。
- “不想动”优先理解为当次希望减少活动负担，不写成“懒惰”等人格标签，不推断疾病。
- 读取已填写的可用时间、所在环境和日程；已有信息不重复问。缺少会影响推荐的关键条件时，仅简短询问一次。
- 在现有适用候选中，优先选择符合时间限制、准备少、步骤简单的行动。它不能突破用户的明确拒绝、任务适用条件或安全规则。

推荐附近显示“本次考虑”：最多3条实际使用的信息，例如“今天有考试安排”“可用2分钟”“希望原地、轻量”。再用一句话解释推荐与这些条件的对应关系。用户能修改条件或在对话中纠正。

这是输入与决策依据摘要，不展示模型内部思维链，不编造拆解过程、分析进度或完成标记。复用已有Agentic结构化输出；没有真实过程事件时只在结果中展示摘要。

## 3. 日程最小实现

采用事件表和新增/编辑表单，不安装完整日历组件。

每条记录保存：事件标识、所属用户、名称、开始日期、结束日期（含当天）、类型、忙碌程度。类型至少含考试、假期、普通安排；忙碌程度可留空。普通安排可填写学习、家庭或兴趣活动。只有日期，无需时区同步、重复事件和外部账户连接。

提供查看、新增、修改、删除，保存后刷新可读回。推荐读取当天生效事件；首页只简短呈现当天安排，详细列表放现有合适入口。

决策优先级：安全与任务适用条件始终先满足；用户当次明确表达优先于日程推测；日程用于补充情境；历史偏好用于候选排序。同日“假期”和“考试”并存时保留两个事实，不直接判定空闲。假期不等于可用20分钟，考试期也不一律限制为同一种任务。

暂时的忙碌或低行动意愿不写成长期偏好。日程名称作为用户数据处理，不作为系统指令。

## 4. 推荐逻辑与任务范围

硬性时间、环境及“不做某类活动”等明确要求用于筛选；“更轻一点、容易开始”在剩余候选中调整优先级。没有合适任务时说明缺少匹配，允许用户修改条件，不生成未经审核的健康行动。
