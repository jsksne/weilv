# 微律 Agent 项目规划与开发阶段基线

> 文件建议路径：`docs/agent/WEILV_AGENT_PLAN.md`  
> 用途：供 Codex、Work Agent、代码代理和后续协作者快速理解“微律”当前技术路线、开发阶段、数据边界与执行规则。  
> 状态：基于 2026-08-10 项目开发文档及其后续讨论整理。  
> 原则：本文件用于“如何推进项目”；若与《核心技术实施基线 v1.1》中的已冻结技术决策冲突，以最新经项目负责人/指导老师确认的决定为准。

---

## 1. 项目一句话定义

**微律**是一套面向初中生和高中生学习场景的个性化健康微行动支持系统。

它不是医疗诊断系统，也不是单纯的健康问答机器人。

核心问题是：

> 在学习压力、时间和精力有限的情况下，系统能否结合当天状态、公共健康知识、个人历史反馈和用户记忆，为不同学生找到当前更容易执行、负担更低、且可解释的健康微行动？

核心产品闭环：

```text
用户画像
+ 当天状态
+ 历史反馈
+ User Memory
+ 当前问题
        ↓
理解问题 / 必要时拆分子问题
        ↓
BM25 + Vector 混合检索
        ↓
Reranker
        ↓
安全与适用性过滤
        ↓
构建 RAG 上下文
        ↓
LLM 生成推荐与解释
        ↓
用户完成 / 跳过 / 替换 / 评价
        ↓
更新 User Memory
        ↓
影响下一次推荐
```

项目最重要的能力不是“每天给几个任务”，而是：

> 系统能否通过持续反馈逐渐知道什么任务、什么时长、什么时间和什么强度，更适合当前用户。

---

## 2. Agent 必须遵守的优先级

Agent 在执行任何任务前，按以下优先级判断：

1. **安全与未成年人数据边界**
2. **项目负责人 / 指导老师已经确认的决定**
3. **核心技术实施基线**
4. **当前 Stage 的目标与验收标准**
5. **合理工程实践**
6. **Agent 自己的技术偏好**

Agent 不得因为“另一套技术更流行”而自行更换已经冻结的技术路线。

如果存在明显不同的合理路线，应：

- 说明差异；
- 说明优缺点；
- 标记为“待确认”；
- 必要时整理为可直接询问指导老师的问题；
- 在确认前不要把未确定方案写成既定事实。

## 3. 已冻结的技术路线

当前竞赛版以以下技术路线为基线。

### 3.1 前端

```text
Vue + Element
```

要求：

- 正式系统必须使用前端框架；
- 不以纯 HTML 页面作为最终系统；
- 第一版优先 Web；
- 具体 Vue / Element 版本和状态管理方案可按合理工程实践确定。

---

### 3.2 后端

```text
Python + FastAPI
```

FastAPI 负责：

- Web API；
- 用户数据接口；
- 用户画像；
- User Memory；
- 任务状态与反馈；
- Elasticsearch 访问；
- Embedding / Reranker / LLM API 调用；
- RAG 流程；
- 安全规则；
- 日志与异常处理。

当前主后端不使用 Spring Boot。

---

### 3.3 数据与检索

竞赛版统一使用：

```text
Elasticsearch
```

ES 同时承担：

- 公共健康知识；
- 审核微任务；
- 用户画像；
- User Memory；
- 行为与反馈日志；
- BM25；
- Embedding 向量；
- Vector Search；
- 测试和评估记录。

当前逻辑索引：

```text
health_knowledge_v1
micro_tasks_v1
user_profiles_v1
user_memory_v1
interaction_logs_v1
evaluation_records_v1
```

第一版不把 MySQL、PostgreSQL、Milvus、Chroma、Pinecone 作为核心依赖。

---

### 3.4 Embedding

当前采用：

```text
阿里云 text-embedding-v4
Embedding dimension = 1024
```

向量写入 Elasticsearch。

若以后修改向量维度，需要重新生成全部向量并重建相关向量索引。

---

### 3.5 混合检索

每个 Query：

```text
BM25 Top 10
+
Vector Top 10
```

Vector Search 使用：

```text
Cosine Similarity
```

两路候选合并、按合理方式去重后进入 Reranker。

---

### 3.6 Reranker

纯文本场景当前采用：

```text
qwen3-rerank API
```

不要恢复成 `qwen3-vl-rerank`，除非后续确实引入多模态需求并重新确认技术方案。

---

### 3.7 RAG 演进顺序

必须按能力逐步升级：

```text
基础 RAG
    ↓
Personal RAG
    ↓
LangGraph Agentic RAG
    ↓
Collaborative Filtering
```

不要从项目第一天直接构建完整 Agentic RAG。

---

## 4. 为什么重新调整开发 Stage

旧技术基线采用 Stage 1～13，技术内容本身基本合理，但实施上有两个问题：

### 问题 A：需求验证过晚

需求问卷不能等到完整产品开发后才做。

需求验证决定：

- 用户到底需不需要这种产品；
- 默认一天几个任务；
- 单任务多长；
- 用户什么时候愿意看到推荐；
- 用户愿意提供哪些数据；
- 用户是否接受 User Memory；
- 个性化是否真的比通用推荐更有吸引力。

因此需求验证必须前置为 **Stage 0**。

### 问题 B：安全规则不能等 RAG 做完才补

基础检索技术 POC 可以先独立验证。

但一旦系统开始向学生输出真实健康微任务：

- 审核任务白名单；
- 适用条件；
- 停止条件；
- 风险分流；
- 求助提示；

必须已经存在。

因此“知识库 + 审核微任务 + 基础安全规则”被合并前置。

# 5. 新的开发路线：Stage 0～10

---

## Stage 0：需求验证

### 目标

回答：

> 微律解决的问题是否真实存在？目标学生愿不愿意使用？MVP 应该长什么样？

### 主要工作

- 明确第一版人群：初中生、高中生；
- 明确第一版场景：学习场景；
- 明确研究负责人、数据用途、保存位置、保存期限；
- 确认学校 / 指导老师要求的伦理、监护人同意流程；
- 先进行 5～8 人问卷预测试；
- 修改用户看不懂的表述；
- 再进行正式需求问卷；
- 根据预先定义的门槛决定 MVP 参数。

### 需求问卷重点决定

- 用户主要健康行为困难；
- 单任务可接受时长；
- 一天可接受任务数；
- 推荐出现时机；
- 提醒方式；
- 愿意提供哪些状态；
- User Memory 接受度；
- 是否希望查看 / 修改 / 删除系统记忆；
- 个性化推荐是否比通用任务更有吸引力。

### DoD / 出口条件

至少满足：

- 目标用户和使用场景明确；
- 预测试完成；
- 问卷理解问题修正；
- 数据与伦理边界明确；
- MVP 默认任务数量、时长等不再纯靠项目组猜测；
- 形成一份需求调研结论。

### 本阶段禁止

- 不用真实问卷结果证明医学效果；
- 不宣称产品改善睡眠、视力或其他健康结果；
- 不因为用户“表示愿意使用”就宣称长期有效；
- 不采集非必要身份信息。

## Stage 1：权威知识 + 审核微任务 + 基础安全规则

### 目标

先回答：

> AI 可以依据什么知识？允许推荐什么？什么情况下应该停止推荐？

### 第一批知识来源

当前 seed sources 优先包括：

- 国家疾病预防控制局；
- 国家卫生健康委员会；
- 教育部；
- WHO；

覆盖：

- 久坐；
- 用眼；
- 户外活动；
- 运动；
- 睡眠；
- 学习间歇；
- 轻量恢复。

### 资料处理流程

```text
发现官方资料
    ↓
核验机构 / 版本 / 链接
    ↓
保存原始文件或网页快照
    ↓
转 Markdown
    ↓
清洗导航 / 页眉 / 无关内容
    ↓
按标题与语义段落切 Chunk
    ↓
补 Metadata 与来源定位
    ↓
人工审核事实、适龄性和安全边界
    ↓
进入可向量化状态
```

### Chunk 初始规则

- 优先沿用官方原文章节；
- 约 400～900 中文字符作为起始范围；
- 不为了凑长度拆开完整建议、条件或警示；
- 必须保存原文定位；
- 超长章节再按语义切分；
- 必要时保留少量上下文重叠。

### 公共知识与微任务必须分开

公共知识回答：

> 什么是正确的？为什么？

审核微任务回答：

> 用户当前可以具体做什么？

`micro_task` 至少应有：

```text
task_id
name
instruction
domain
duration_minutes
intensity
scenarios
exam_week_fit
allow_conditions
stop_conditions
source_chunk_ids
review_status
```

只有：

```text
review_status = approved
```

的任务才允许进入正式推荐候选。

LLM 可以辅助起草任务，但不能自己创造未经审核、可直接推荐的新健康任务。

### 安全规则最低要求

- 输入风险分流；
- 审核任务白名单；
- 年龄 / 状态 / 场景 / 风险标签过滤；
- 输出校验；
- 求助提示；
- 规则触发审计；
- 来源可追溯。

出现明显疼痛、严重不适、急性风险或求医需求时：

```text
停止普通任务推荐
↓
进入保守求助提示
```

### DoD / 出口条件

至少：

- 首批 ≥6 份官方资料通过来源核验；
- 七个健康领域都有明确扩展计划；
- 任一 Chunk 可追溯到原始文档和具体位置；
- 公共知识与审核微任务严格分开；
- 第一批审核微任务可用于测试；
- 基础安全规则已经结构化。

## Stage 2：Embedding / Reranker / Elasticsearch 技术 POC

### 目标

暂时不造完整产品，只验证核心基础设施能否正常工作。

### 分别验证

#### Elasticsearch

- 建索引成功；
- 写入文本；
- 写入向量；
- BM25 可查询；
- Vector Search 可查询；
- Metadata filter 可用；
- 数据可按来源追溯。

#### text-embedding-v4

- API 调用成功；
- 输出 1024 维；
- 批量向量化流程可重试；
- 失败不会丢失已经审核的原始文本。

#### qwen3-rerank

- API 调用成功；
- 能给候选重新排序；
- 能查看输入候选和重排结果；
- API 不可用时测试环境允许明确降级，但正式演示不可静默降级。

#### LLM

- 基础 API 调用成功；
- 可以接收带来源 RAG Context；
- 暂时不承担自由生成健康任务。

### 数据

优先使用：

```text
真实权威知识
+
审核任务
+
合成用户
```

不用真实未成年人健康行为数据完成技术 POC。

### DoD / 出口条件

- ES / Embedding / Reranker / LLM 均有独立可运行测试；
- 所有模型调用有错误处理；
- 能查看实际检索结果，而不是只有“接口成功”；
- 技术 POC 有最小自动测试。

## Stage 3：基础 RAG

### 目标

证明：

> 在不知道复杂个人历史的情况下，系统是否能够从正确知识中找到相关内容，并安全地产生有来源的推荐。

### 第一版固定链路

```text
用户问题 / 子问题
        ↓
BM25 Top 10
+
Vector Top 10
        ↓
按合理规则合并去重
        ↓
qwen3-rerank
        ↓
安全与适用性过滤
        ↓
审核微任务候选
        ↓
构建带来源 RAG Context
        ↓
LLM
        ↓
推荐 + 推荐原因 + 来源
```

### 子问题拆分

复杂问题可以拆成多个子问题后分别检索。

但不要把“必须使用 LLM 拆分每一个问题”写死。

简单问题允许直接检索。

### 调试要求

必须能够查看：

1. 原始 Query；
2. 子问题；
3. BM25 Top 10；
4. Vector Top 10；
5. 合并去重结果；
6. Reranker 排序；
7. 被安全规则移除的候选及原因；
8. 最终 RAG Context；
9. 来源。

### DoD / 出口条件

- 至少多组真实问题可以运行完整链路；
- 每条最终知识能回溯来源；
- 推荐只能来自审核任务；
- 风险场景可以阻止普通推荐；
- 能区分 BM25 / Vector / Reranker 每一步发生了什么。

### 本阶段禁止

- 不实现协同过滤；
- 不急着使用 LangGraph；
- 不把 User Memory 错误混进公共知识索引；
- 不因为最终输出看起来合理就认为 RAG 已正确。

## Stage 4：User Memory + Personal RAG

### 目标

证明：

> 同一个用户在产生反馈后，下一次推荐会因为“系统了解了他”而发生合理变化。

### User Memory 可能包含

```text
基础画像
考试状态
可用时间
任务类型偏好
任务时长偏好
任务强度偏好
历史接受
历史完成
历史跳过
历史替换
用户主动评价
系统形成的行为规律
```

### Personal RAG 的最低要求

个性化不能只是：

> 最后让 LLM 换一种说法。

用户数据应真正影响至少部分：

- Query；
- Metadata filter；
- 个人记忆检索；
- 候选任务；
- 推荐排序；
- 最终输出。

### 最小纵向测试

```text
合成用户：
考试周
今天只有5分钟
过去多次跳过10分钟任务
        ↓
系统推荐
        ↓
用户反馈：“太长 / 没时间”
        ↓
写入 User Memory
        ↓
再次提出类似需求
        ↓
系统优先选择更短任务
```

### DoD / 出口条件

- User Memory 与 Public Knowledge 分开；
- 不同用户数据严格隔离；
- 用户反馈成功写回；
- 第二轮推荐能展示合理变化；
- 可以解释“哪些记忆影响了本次推荐”；
- 支持查看 / 修改 / 删除用户记忆的产品设计。

## Stage 5：Vue + Element Web 闭环

### 目标

将已经跑通的后端能力组合成真正可以演示的 MVP。

### 核心页面优先

```text
今日任务
当前状态输入
AI 健康助手
任务来源与推荐原因
完成 / 部分完成 / 跳过 / 替换
我的 User Memory
基础个人设置
技术链路展示（比赛演示）
```

### 前端连接规则

```text
Browser
   ↓
FastAPI
   ↓
Elasticsearch / Model APIs
```

浏览器不能直接访问 Elasticsearch。

### DoD / 出口条件

不能只以“代码已经生成”为完成。

至少：

- 项目可启动；
- 页面实际可访问；
- 关键闭环可操作；
- 前端与真实 FastAPI 接通；
- 完成 / 跳过能写回；
- 下一次推荐能体现反馈；
- 浏览器 Console 无关键错误；
- 自动测试与人工冒烟测试完成。

## Stage 6：模型结果质量评估

### 目标

回答：

> 个性化推荐是否真的比简单通用推荐更符合用户需要？

### 推荐对照

同一组场景，匿名、随机顺序比较：

```text
A. 通用审核任务推荐

B. 加入当天状态的推荐

C. 当天状态 + 可控 User Memory 的 Personal RAG
```

评价：

- 相关性；
- 个性化；
- 可执行性；
- 负担程度；
- 解释清晰度；
- 采用意愿；
- 安全感 / 信任。

### 轻量工程验证

项目不以 Recall@K / MRR / NDCG 作为主要比赛评价。

但保留工程测试：

- 50～100 个有人工来源标注的问题，检查检索与引用；
- ≥30 个风险场景检查安全分流；
- 记录端到端响应时间。

这些只用于工程质量控制，不用于证明医学干预效果。

### DoD / 出口条件

- 有通用 vs Personal RAG 的对照结果；
- 知道 Personal RAG 是否真正产生用户可感知价值；
- 已记录主要失败类型；
- 已完成安全风险样例测试。

---

## Stage 7：LangGraph Agentic RAG

### 前置条件

只有以下条件满足后才进入：

- 基础 RAG 稳定；
- Personal RAG 稳定；
- User Memory 读写稳定；
- 已有固定流程的评估基线。

### 目标

Agent 不再机械执行固定链路，而是决定：

```text
这次问题是否需要拆分？
↓
需要查公共知识吗？
↓
需要查 User Memory 吗？
↓
已有结果够不够？
↓
不够 → 改 Query / 再检索
↓
够 → 生成推荐
```

### LangGraph 负责

- 状态管理；
- 检索计划；
- 条件分支；
- Query 改写；
- 必要时重新检索；
- Public Knowledge / User Memory 工具调用；
- 结果充分性检查。

### 本阶段禁止

- 不因“Agentic”听起来更高级就增加无意义节点；
- 不允许 Agent 绕过审核任务库和安全规则；
- 不把所有简单问题强制进入复杂 Agent loop。

### DoD / 出口条件

- LangGraph 工作流可观测；
- 每个节点输入输出可调试；
- 简单问题不会无意义循环；
- 重检索有明确停止条件；
- 安全规则不可被 Agent 绕过。

---

## Stage 8：Agentic RAG 对照验证

### 目标

不是证明“Agentic RAG 一定更先进”，而是回答：

> 在哪些复杂问题上，Agentic RAG 相比固定 RAG 真正带来了价值？

比较：

```text
固定 RAG
VS
LangGraph Agentic RAG
```

关注：

- 复杂多条件问题；
- 第一次检索信息不足的场景；
- 需要 User Memory 与 Public Knowledge 组合的场景；
- 是否减少明显不相关结果；
- 是否引入不必要延迟；
- 是否发生循环或过度检索。

如果 Agentic RAG 没有明显提升，比赛材料不得只凭技术名称宣称更优。

---

## Stage 9：协同过滤

### 前置条件

协同过滤不是第一阶段依赖。

它真正需要的数据是：

```text
User × MicroTask × Feedback
```

例如：

```text
user_001 + task_005 + completed
user_001 + task_008 + skipped_too_long
user_002 + task_005 + completed
```

只有积累到足够真实交互以后，协同过滤才有真实业务意义。

### POC 可以提前做什么

可以：

- 使用合成用户；
- 使用合成 User × Task 交互；
- 用 MovieLens 学习 / 验证协同过滤代码；
- 测试 User-based / Item-based 等基础算法。

但 MovieLens 只能证明：

> 协同过滤算法代码可以运行。

不能证明：

> 微律对青少年有效。

### 正式加入系统以后

三层个性化：

```text
知识相关性
RAG
+
个人历史
User Memory
+
相似用户行为
Collaborative Filtering
```

## 7.3 公开数据不能直接做什么

CEPS / YRBSS / GSHS / PISA 等一般没有：

```text
当前用户
对微律 task_id

```

因此它们不能直接替代：

```text
user_memory_v1
```

也不能直接成为微律真实协同过滤数据。

## 7.4 推荐数据路线

```text

        ↓

        ↓

        ↓

        ↓

        ↓
Personal RAG / CF POC
        ↓
产品与安全成熟
        ↓
合规的小规模真实试用
        ↓
匿名最小必要交互数据
```

任何合成数据都必须明确标记：

```text
synthetic = true
```

不得伪装成真实用户、真实问卷或真实实验结果。

# 8. 真实未成年人数据边界

当前技术 POC 不需要真实未成年人健康数据。

在真实采集前必须确认：

- 学校 / 指导老师的研究要求；
- 是否需要伦理审查或备案；
- 监护人知情同意；
- 学生能够理解的参与说明；
- 数据最小化；
- 数据保存地点；
- 数据访问人；
- 保存期限；
- 删除机制。

默认不要采集：

- 姓名；
- 手机；
- 邮箱；
- 精确学校 / 班级；
- 住址；
- 定位；
- 身份证号；
- 医疗诊断；
- 用药信息。

用户主动报告健康状态时，只收集完成当前安全判断和推荐所必需的信息。

# 9. Agent 工作方式

## 9.1 语言与解释

## 9.2 技术决策

遇到三个层级：

### A. 已冻结

直接遵守，不自行替换。

不得自行拍板。

需要整理成：

> 老师，我们目前有 A 和 B 两种方案。它们分别……。考虑到竞赛 MVP，我们倾向于 A，请问是否按 A 实施？
